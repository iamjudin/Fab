# Decision and continuation policy
Applies to Product and Wireframe and overrides inherited stage-specific approval
wording. Stage references define meaning/dependencies, not an approval after each
file/entity. This is the canonical boundary for WF-17.

Continue authorized work until requested outcome is complete, a genuine human
choice blocks it, a tool/access condition blocks it or the budget/permission ends.
A checkpoint saves progress; it is not a reason to yield. Inform about impact,
then continue. No approval merely because the next stage has a name.

New product: infer known intent/flexibility/non-goals from input. Only missing
human-owned choices that change the next result require questions. A clear
request to explore/build a candidate authorizes candidate artifacts, not invented
creator acceptance. Existing/partial request accepts available requirements/
accepted artifacts; no mandatory HJ/BJ or new full brief before bounded work.
Jobs are developed when they help a new product decision, not to satisfy a schema.

HJ/BJ/Core may be judged as one coherent decision when actually one choice.
Keep their distinct entity meanings and typed links. Focused HJ/BJ review can
still remain standalone when requested; don't invent acceptance to advance.
Machine validation and author preflight are autonomous, not human approvals.

Structure → scenario → visible layout remain semantic dependencies. Use existing
accepted versions; for a requested end-to-end candidate route continue with
explicit candidate assumptions if no blocking human tradeoff remains. Don't label
this as creator acceptance. If new choice affects hierarchy/access/experience,
expose it before dependent work. In tests simulated operator choices are evidence
of the test setup, never real human usability/taste approval.
