# Landing pages

## Apply to the active object

Use for a public promotional/offer page that helps a visitor understand an offer
and take an intended action. A browser target, homepage, the word landing, or a
landing elsewhere in the project does not make an application screen a marketing
page. Reassess the active object when the task changes; preserve unrelated pages,
app behavior and accepted decisions. This profile does not replace app navigation,
state, persistence, platform or recovery rules.

## Direct outcomes and content

Use the current skill for the requested result: Product for missing offer/visitor/
action meaning, Wireframe for section hierarchy/composition, Prototype for an
interaction experiment, Delivery for actual implementation, Analysis for review.
Cowork can orient an unclear task; it is not an obligatory gateway.

Accepted input counts. Clarify only missing decisions that change dependent work.
For a bounded page, a section map can be sufficient: connect section purpose,
visitor need, supplied content, evidence/gap and intended action. Do not force a
full product graph, numbered interview, review canvas, grayscale pass, fixed
problem/solution/proof sequence or Figma route before the requested result.
Actual domain or navigation complexity still needs sufficient behavior modeling.

Preserve approved or locked copy. A content-writing request authorizes drafts;
a layout-only request does not authorize rewriting accepted text. Keep new draft
copy and assumptions identifiable. Do not invent facts, customers, metrics, logos,
testimonials, guarantees or integration claims. Missing proof remains a gap; it
does not require a proof section. Interpret references as design decisions rather
than borrowing another product's claims.

## Plain web first

For a new landing without an explicitly chosen stack, start with semantic HTML,
ordinary CSS and vanilla JavaScript only for behavior HTML/CSS cannot sufficiently
provide. Typical files are `index.html`, `styles.css`, optional `script.js` and
local assets; this is an example, not a required file count. Reuse CSS variables,
roles and classes for coherent growth. A simple stack is not permission to reduce
design quality, responsiveness or accessibility.

Do not automatically introduce an application/CSS framework, component library,
package manager, bundler, transpiler, CMS, hosted builder or CDN dependency.
Prefer system fonts unless accepted brand assets or a concrete requirement justify
another source. Do not add remote fonts, tracking or third-party runtime scripts
merely because they are familiar. Preview servers and testing tools do not by
themselves require product dependencies.

An explicit target stack or existing repository takes precedence over this new-
project default. Inspect and retain its working stack, brand, tokens and components;
do not migrate it to plain HTML automatically. When a new requirement exceeds the
baseline, explain the actual unmet need, smallest viable alternative and relevant
maintenance consequence. Discuss a material stack/scope choice before adopting
it; routine HTML/CSS/JS decisions need no repeated approval. This is a sufficient
starting point, not a product-size ceiling or permanent technology restriction.

## Check the promised surface

Check the requested output: content fidelity and action meaning for structure;
actual narrow/wide rendering, long text, keyboard focus and navigation for an
executable candidate. Retain meaningful content and usable navigation without
JavaScript where practical. Include relevant validation, error/retry and return
paths when interactions are present. Use existing visual foundations; repeated
patterns should remain coherent without importing an archived naming scheme.

HTML alone does not provide remote submission, lead storage, email, payments or
other server operations. Identify that specific dependency before promising it;
do not silently choose a backend or present simulated success as real delivery.
Draft/local preview, public deployment, indexing, social previews and tracking
have separate needs and authority. Do not invent domain URLs, verification values
or analytics IDs, or require every SEO asset/service for every page. Check current
primary guidance for the actual stack/service when those outputs are requested.

Use current Figma skills when editable Figma output is requested; distinguish
capture/reference from the promised editable artifact. No code-first round trip
is required. Report actual observations and unverified paths; a screenshot or
section map does not prove backend behavior, comprehension or conversion gains.
Without product-code evidence, label a proposed implementation cause as a
hypothesis rather than a confirmed diagnosis.
