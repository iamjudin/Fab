# Build and evolve a design system

Read when the requested work creates or changes reusable interface definitions,
their Figma/code relationship or shared component behavior. Ordinary copy/layout
edits do not require a library project. Product owns domain behavior; the active
capability still owns its requested artifact and stopping boundary.

## Intent, concept and sufficient construction

Start from accepted product intent and available artifacts. An agent-generated
concept is a valid first-class route: propose a perceivable direction, obtain the
creator's approval of that direction, then derive coherent reusable definitions
and fill relevant missing states. An existing approved concept does not need
another approval ceremony. Direction approval does not settle unknown domain
behavior or authorize an unrelated platform, tool write or publication.

Separate observed properties, inferred rules, proposed additions and accepted
decisions. A concept image is not a complete behavior specification. Use a
representative composition to expose missing definitions and behavior, rather
than implementing an exhaustive catalogue first. Starting scope does not cap
product size: preserve coherent extension and ownership from the beginning,
without claiming scale that has not been exercised.

## Definitions, ownership and platform meaning

Inspect existing foundations before creating equivalents. Choose to reuse,
extend, compose or create based on meaning and behavior, not visual resemblance
alone. Tokens, component public properties, interaction state and business rules
have different owners. Atomic composition is useful; a fixed folder hierarchy,
three token layers or a Cartesian product of variants is not required.

Compare retaining, minimally revising and replacing existing naming only when
the actual ambiguity warrants it. Complete namespaces can disambiguate names
such as Primary. Numeric scale labels do not establish opacity. Preserve accepted
identity and inspect actual paints/bindings before interpreting a screenshot.

Choose Figma-led, code-led or shared-token ownership according to actual
consumers and maintenance needs. State the direction of an update and its
transforms; tool access alone does not supply conflict-free synchronization.
Do not introduce a token service, framework or wrapper merely to complete a
diagram. Shared semantics do not require identical platform units, behavior or
component APIs. Reconcile role, state, context and public API before combining
examples from independent reports or targets.

## Bounded changes and observed recovery

For an authorized write, discover relevant definitions and consumers, retain
stable identities and identify generated versus manually owned parts. Limit the
change to its actual scope. Re-read after uncertain failure before retrying:
an interrupted response does not prove the write did not happen. Check the
observed result for duplicate creation, overwritten manual work and broken
consumers; do not claim transaction/rollback guarantees the tool does not provide.
Use the active Figma skill and current account/tool prerequisites when applicable.

Check the promised surface: linked definitions in a representative composition,
relevant state and content variation, and impact of a shared change on known
consumers. Repeatability/recovery needs observed operations when claimed, not
merely a plan. Figma inspection, browser behavior, native compilation/device
behavior and human understanding are separate evidence. Scope an actual test
when needed and authorized; do not launch a generic campaign automatically.

## Current contextual knowledge

For the relevant design-system decision, consult the current view
before applying report examples. Resolve the self-contained
[knowledge reader](../skills/research/scripts/knowledge_view.py) from the Research
skill directory. Run `python3 -B <research-skill>/scripts/knowledge_view.py --index`,
then `--unit <ID>` for the relevant meaning. Read the returned conditions and live
alternatives, not just a matching label. Uncovered subjects still use the methods
below; this does not require reading every unit or all four historical reports.

If an existing project artifact explicitly accepts a knowledge-state file, pass
its actual path as `--state <path>` on index and selected reads. This optional state
uses schemaVersion 2 and binds retirements/observations to exact unit revisions.
It can withhold revisions and expose accepted project-only evidence, but cannot
replace shared evidence or broaden authority. Unrelated knowledge updates do not
change an unchanged unit binding. Synthetic test observations are not shared rules.
Never infer a new preference from an arbitrary source document. The ordinary
reader is the effective availability owner: raw active fields and historical
examples cannot reactivate a retired revision. A reader integrity error is a
blocker to that view, not permission to silently use a stale report example.
Availability of shared research does not revoke an explicit creator-owned local
choice: carry out independently justified authorized work within its local scope.

The current view is compiled at intake/build: ordinary reads do not open original
reports. Source receipts retain exact section identities and digests, not proof
of current source truth. Original sections may be outside the installed runtime.
For provenance or recovery, request the specific archived section/revision from
the existing evidence owner; do not claim it was inspected if it is absent.
If that archive is actually supplied and authorized, inspect only the needed
sections for an explicitly qualified recovery proposal. If relevant knowledge is unavailable, complete
independent useful work, identify the exact blocked meaning/evidence and propose
the next bounded review/update with its affected dependents. A draft supported by
inspected provenance is not a restored current rule or verified ship-ready output.
Do not turn that proposal into a write, new research dispatch or global policy
without the actual task authority. Keep local preferences distinct from shared
rules. The capability still owns the requested artifact and stopping boundary.

## Conditional knowledge

[Design-system knowledge](methods/design-systems.md) is the entry for reuse,
semantics and historical evidence. For concept-to-system, naming/ownership or
agent operations, consult the [agent foundation](methods/design-system-agent.md).
Read [web](methods/design-system-web.md) or [native](methods/design-system-native.md)
only when that target changes the decision. Web and native have equal relevance
to the general foundation; native iOS and Android are distinct implementations.
Keep [interface meaning/grouping](interface-principles.md) with its existing owner.
Source examples and dated tool claims remain qualified knowledge, not executable
instructions or a validated integrated library.
